## Deviations and Remaining

- No reviewed F06-S03 behavioral deviation was introduced.
- F06 does not implement a real NIC. The integration treats a Local Transport-delivered request as
  the source-ready boundary, tests the required flush-before-publication order, and exercises the
  real A10 Host flush API. A future NIC transport must invoke the same gate only after consuming
  the corresponding NIC completion.
- The benchmark uses an in-process CUDA mapping backend so Client and daemon device virtual
  addresses are identical. Cross-process CUDA IPC mapping correctness remains covered separately;
  the no-key-path-Mock public API composition belongs to F07.
- Payload setup and final correctness verification are deliberately outside the persistent-kernel
  measurement interval. A synchronous CUDA operation in the same context must not be issued while
  this non-preempted persistent kernel is active; callers must prepare before `start` and verify or
  otherwise synchronize after `wait`.
- The selected model remains limited to one CTA and inherits the F06-S02 small-payload trade-off.
  The end-to-end result is materially below the isolated copy-core result because it also includes
  posting, two Loop Workers, parent aggregation, Host batching/flush, and response handling.

### Bounded Ampere mbarrier Wait Follow-Up

Investigation localized the approximately 1.048 ms sparse-pipeline latency to libcu++'s
unbounded `wait_parity()` software backoff on the A10. Its SM86 path polls
`mbarrier.test_wait.parity` and can eventually issue `NANOSLEEP 0xf4240`, corresponding to a
1,000,000 ns sleep. This was independent of copy size: one-byte and 8 KiB single-task pipeline
runs both measured approximately 1048.46 us P50, while the atomic-claim model did not.

The pipeline now retains its mbarrier/phase protocol but replaces all five unbounded parity waits
with one `try_wait_parity_for(..., 0 ns)` test followed by a fixed 64 ns `__nanosleep` on failure.
The A10 SASS no longer contains the 1 ms sleep. Timed 256 ns polling, 32 ns sleep, and 16-test
pre-poll variants were evaluated; the single-test/64 ns form gave the best measured balance
between sparse latency, implementation simplicity, and saturated throughput.

With the same 30-copy-warp, shared-depth-16 QD1 latency configuration:

### In-Process CUDA Worker Bandwidth/Latency Split Follow-Up

The production-backend microbenchmark no longer reports per-WR latency from its saturated QD64
run. At that queue depth the measured interval is dominated by queue residence, so it is not a
useful copy-path latency metric. The current benchmark instead runs two independent phases:

- `phase=bandwidth` uses QD64 and signaling interval 32. It does not timestamp individual WRs and
  reports parent MWR/s, payload MTask/s, and logical GB/s.
- `phase=latency` uses QD1 and signals every WR. It independently measures an 8 KiB WR containing
  one 8 KiB payload and a 64 KiB WR split into eight 8 KiB payloads, and reports
  min/max/average/P50/P99/P99.9 latency from daemon submission through parent CQ-entry production.

The bandwidth phase uses 64 KiB logical WRs split into eight 8 KiB payload tasks. Each bandwidth
or latency case uses 1,000 warm-up WRs and 10,000 measured WRs. The cases independently verify
parent-request, payload-task, completion, response, and CQ-entry conservation as well as copied
data and guard regions.

The first QD1 implementation exposed a Host batching defect: `LoopWorker` submitted one payload
per progress call and relied on the backend's 50 us maximum batch-age timer to publish a partial
batch. That produced approximately 61--63 us P50. Reducing the timer alone lowered latency but
also caused repeated undersized CUDA queue publications and cut saturated throughput.

The corrected path batches at the Worker boundary. A requester progress call expands as many
currently available WR payloads as the transport can accept. The responder drains the currently
available payload requests into the backend, then explicitly release-publishes the accumulated
CUDA task batch once. Available CUDA completions, parent responses, and requester responses are
also drained in batches. The 50 us maximum batch age remains only as a safety trigger for a caller
that does not explicitly close its current submission batch; it is not on the normal LoopWorker
path.

Three A10 Release runs produced:

| 1 | 23.826594 | 0.363565 | 2.908520 | 11.345 | 12.880 | 13.097 | 13.307 |

now provides fixed-array `try_submit_batch` and `try_pop_completion_batch` operations with scalar

requests, submits the available prefix in one call, retains any unaccepted suffix across

### Client-to-Daemon API E2E Follow-Up

The earlier CUDA Worker measurements are in-process microbenchmarks. They call the internal WR
posting helper, directly drive both LoopWorkers, and stop latency timing when the requester
produces a parent completion. They do not include the public Client API, a process boundary, or
`ugdr_poll_cq`. They are retained as component baselines but are no longer described as full
Client-to-daemon E2E results.

`ugdr_client_daemon_cuda_benchmark` adds the missing public-API boundary. The Client and daemon
harness run in separate processes and communicate through the normal control socket and
shared-memory data queues. The measured bandwidth path has these semantics:

- The Client links 64 signaled/unsignaled 64 KiB RDMA Write WRs into one `ugdr_post_send` call.
  The public API release-publishes all 64 WQEs into the shared lock-free SQ.
- The requester LoopWorker consumes exactly one SQ slot at a time and splits each WR into eight
  8 KiB payload requests. The responder uses the 64-entry backend batch API added above.
- Only the final WR in each ordered 64-WR batch is signaled. The Client spins in the public
  `ugdr_poll_cq` API until it receives that final CQE; by same-QP ordering, that CQE closes the
  entire batch. Thus CQ processing is one entry per 64 WRs rather than one entry per WR.
- Setup and final correctness validation use CUDA memcpy, but no CUDA memcpy is inside a timed
  bandwidth or latency interval. Every run compares the full 64 KiB target with the source after
  the final CQE.

QD1 latency separately signals and polls every WR. Its timer starts immediately before the public
`ugdr_post_send` call and stops only after the matching public `ugdr_poll_cq` call returns a
successful WC. The 8 KiB case contains one payload; the 64 KiB case contains eight payloads.

Three A10 Release runs used 100 warm-up bandwidth batches, 1,000 measured batches (64,000 WRs and
512,000 payload tasks), 100 QD1 warm-up WRs, and 5,000 measured latency WRs per size:

| 1 | 28.062205 | 0.428195 | 3.425562 | 11.238 | 14.821 | 13.306 | 14.824 |
| 2 | 27.968304 | 0.426762 | 3.414100 | 11.325 | 14.500 | 13.411 | 14.907 |

case covering the 64-WR final-signaled completion rule and full-payload correctness.

### Client E2E WR-Size Sweep

The Client-to-daemon bandwidth phase now accepts any 8 KiB-aligned WR size through 64 MiB and, by
default, sweeps powers of two from 8 KiB to 64 MiB. Every case retains QD64, one linked
`ugdr_post_send` call per 64-WR batch, one final-signaled CQE, and 8 KiB payload splitting. To make
the sizes comparable without transferring multiple terabytes at the large end, the default run
selects enough measured batches to copy at least 4 GiB per size and enough warm-up batches to copy
at least 512 MiB. A single batch is the minimum, so the 64 MiB case naturally transfers 4 GiB per
measured batch. `--wr-bytes`, `--warmup-batches`, and `--bandwidth-batches` remain available for a
focused case.

Three A10 Release sweeps produced the following median public `ugdr_post_send` to
`ugdr_poll_cq` bandwidth:

| WR size | Payloads per WR | Median GB/s |
|-:|-:|-:|
| 8 KiB | 1 | 7.996480 |
| 16 KiB | 2 | 15.596103 |
| 32 KiB | 4 | 23.067199 |
| 64 KiB | 8 | 28.209174 |
| 128 KiB | 16 | 34.020232 |
| 256 KiB | 32 | 37.229598 |
| 512 KiB | 64 | 38.421691 |
| 1 MiB | 128 | 39.722088 |
| 2 MiB | 256 | 40.122231 |
| 4 MiB | 512 | 32.293825 |
| 8 MiB | 1,024 | 33.294444 |
| 16 MiB | 2,048 | 33.361862 |
| 32 MiB | 4,096 | 33.383808 |
| 64 MiB | 8,192 | 33.385173 |

Larger WRs clearly amortize the per-WR API, SQ, parent-state, response, and CQ costs through 2 MiB.
The A10 reports a 6 MiB L2 cache. Because this controlled sweep reuses the same source and target
range for all 64 WRs, a 2 MiB WR has a 4 MiB combined source/target working set, while a 4 MiB WR
has an 8 MiB combined working set. The repeatable 2-to-4 MiB drop is therefore consistent with the
`.cg` copy path leaving the L2-resident regime; this is an inference from the capacity boundary,
not a hardware-counter attribution. From 8 through 64 MiB the result is already flat at roughly
33.3--33.4 GB/s, so 64 MiB is sufficient to establish the large-working-set plateau. A future
stage-ring benchmark with distinct source/target regions per outstanding WR may reach that plateau
at a smaller individual WR size.
