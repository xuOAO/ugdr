## Delivered

- Added the internal `CudaBatchCopyBackend` with one nonblocking CUDA stream, four reusable
  event slots, fixed parent-aligned batches of at most 64 payloads, bounded pending/completion
  storage, and no hot-path allocation.
- Each submitted batch uses `cudaMemcpyBatchAsync` followed by one event record. Event polling is
  newest-to-oldest, while payload completions remain FIFO and preserve their parent request and
  payload indices. A parent may span multiple batches; Loop Worker remains the sole WR-level
  completion aggregator.
- The cuda-batch path does not call the persistent backend's Host GPUDirect RDMA visibility gate.
  Submission remains downstream of the existing Loop Worker source-ready/request-consumption
  boundary and uses `cudaMemcpySrcAccessOrderStream` with default copy flags.
- Runtime batch, event-record, event-query, initialization, and shutdown failures converge through
  deterministic stream cleanup and one error completion per accepted payload.
- Added fake-runtime unit coverage; real A10 D2D coverage for 1/63/64/65 payloads, 8/64 KiB,
  aligned/unaligned pointers, parent isolation, and tail drain; and the same Loop Worker fixture
  for persistent and cuda-batch, including a 65-payload parent WR.
- Added `--backend persistent|cuda-batch` to the client-daemon benchmark. Persistent remains the
  default. Output records backend, batch/slot configuration, batch occupancy, event-query counts,
  process CPU usage, and external profile fields.

## A10 A/B Observation

Executed on 2026-08-12 with NVIDIA A10, driver `575.57.08`, CUDA Toolkit `12.8.93`, Runtime API
`12080`, Driver API `12090`, and a CMake `Release` build. Both paths used 64 KiB parent WRs split
into eight 8 KiB payloads, queue depth 64, 10 warm-up batches, 100 measured batches, 100 latency
warm-ups, and 1,000 latency samples. These are observations, not performance thresholds.

| Backend | Parent MWR/s | Payload MTask/s | Logical GB/s | 8 KiB P50/P99 us | 64 KiB P50/P99 us |
|-|-:|-:|-:|-:|-:|
| persistent | 0.423614 | 3.388914 | 27.761987 | 11.222 / 14.716 | 13.340 / 14.772 |
| cuda-batch | 0.032535 | 0.260279 | 2.132205 | 10.069 / 11.259 | 33.600 / 35.014 |

The cuda-batch run submitted 9,240 batches and 66,220 payloads across bandwidth, warm-up, and
latency phases. Mean fixed-slot occupancy was `0.111979`; 26,040 event queries included 16,805
not-ready results. External `/usr/bin/time` recorded persistent at 0.21 s user + 0.54 s system
over 0.77 s wall time, and cuda-batch at 0.63 s user + 0.54 s system over 0.96 s wall time.

CUDA 12.8 Nsight Systems traces of the single-process backend correctness fixtures observed two
persistent pipeline-kernel instances totaling 316,291 ns. The cuda-batch fixture made 22
`cudaMemcpyBatchAsync_v12080` calls totaling 3,845,244 ns of Host API time and contained no CUDA
kernel records. This establishes the selected API path and absence of the UGDR persistent kernel;
it does not establish zero SM activity inside the CUDA implementation.

Direct SM Active and copy-engine utilization counters could not be collected because the host
denied GPU performance-counter access (`ERR_NVGPUCTRPERM`). The counter limitation is an
environmental profile gap, not a correctness or implementation failure. Timeline reports are in
`/tmp/ugdr-f06-s04-persistent-copy-test.nsys-rep` and
`/tmp/ugdr-f06-s04-cuda-batch-copy-test.nsys-rep` for this workspace session.
